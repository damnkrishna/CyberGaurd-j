# Fuzzing

## My Understanding

According to me, fuzzing refers to sending a large volume of data to a website, any endpoint, or any input point, and seeing how the website responds to such a huge amount of input. This helps in finding bugs that were not expected, and also helps find what happens when very random/unexpected inputs are sent in.

## Types of Fuzzing

### 1. Discovery Fuzzing
Sending huge amounts of data / brute-forcing hidden directories, files, subdomains, API endpoints, parameters, or virtual hosts by throwing wordlists at a target and looking at response codes/sizes.

**Tools:** ffuf, gobuster, dirsearch, feroxbuster, wfuzz

### 2. Input Fuzzing
Sending malformed/unexpected/boundary-case input into forms, parameters, headers, JSON bodies, etc. to trigger errors, bypass logic, or find injection points (SQLi, XSS, SSTI, command injection, buffer overflows in compiled targets).

**Tools:** Burp Intruder, ffuf (again), wfuzz, radamsa, AFL++/libFuzzer (for binaries, not web)

Fuzzing finds the vulnerabilities of endpoints that you might never be able to find on your own — it finds them by sending so much data at a time. This is considered Step 1 of recon.

## My Recon Process (as of now)

1. First find the IP address or website name.
2. Since these processes take too much time — as soon as I'm sure about the IP — start an active scan on that IP using Burp Suite Professional.
3. Start fuzzing on that IP using my own wordlist — one I think will be suitable for this specific website.

## Optimization Matters

Earlier, the websites I worked with were all of the same type. But now, some are healthcare, some are banking, some are different. So sending the type of traffic that will be best suited for that specific website is an optimization that will always help — better than just sending random data.

Optimizing and decreasing the time it takes improves a hacker's capacity and skills. Since these two processes (active scan + fuzzing) take a lot of time to run, meanwhile I'll have to manually try to find bugs on the website myself — the tools might find something, but my own skills will always be more useful in the future than any tool ever could. So: **learn skills, not just tool usage.**

## After the First 3 Steps

After discovery fuzzing, active scanning, and input fuzzing are done, the next process depends on the website. Whatever we find, we try to find out more about that specific bug and how we can exploit it to find something deeper inside — and that's where the game gets interesting.

## Extra (Things to Remember)

- **Permission matters more than "public."** A website being public just means anyone can *browse* it — it doesn't mean you're legally allowed to fuzz/scan it. Get explicit, written go-ahead from your friend (ideally over text/email so there's a record) before pointing ffuf or Burp at his live site.
- **Get that "wow" moment safely first.** Intentionally vulnerable practice targets like DVWA, OWASP Juice Shop, or boxes on HackTheBox/VulnHub will actually show you real findings — faster and with zero legal risk — while you wait for your friend's link.
- **Check scope basics before firing tools.** Look at `robots.txt`, any published bug bounty/security policy, and rate limits before fuzzing even a permitted target — healthcare and banking sites especially may have monitoring that flags aggressive scans.
- **Your terminal issue is probably not malware.** Random/odd characters after an update usually points to a broken locale (language/region) package, not a compromise. Try `locale` to check current settings and `sudo dpkg-reconfigure locales` to reset it before assuming the worst.
- **Skill layer under the tool layer:** alongside fuzzing tools, it's worth learning how raw HTTP requests/responses work, common status codes, and how to read a request manually in Burp's Repeater tab — that's the actual "skill" you mentioned wanting to build, versus just running a tool.
